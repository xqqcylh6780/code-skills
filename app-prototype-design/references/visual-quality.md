# Visual Quality for App Prototypes

## Design from product character

Derive the visual language from the product's content, audience, supplied assets, and existing UI. Do not default to a generic SaaS palette, purple-blue gradient, excessive glass, or a stack of indistinguishable rounded cards.

Use a small token system for surface, elevated surface, text, muted text, divider, primary action, positive, warning, destructive, and one optional signature color. A user-requested color removal must update every token and hard-coded chart or illustration color, including dark mode.

## Hierarchy and density

- Give each screen one unmistakable primary action.
- Let typography, spacing, and alignment establish hierarchy before adding containers.
- Use cards only when grouping improves comprehension.
- Give data-heavy screens compact but scannable comparison structures.
- Preserve safe-area space around status bars, navigation bars, sticky actions, and sheets.
- Keep tap targets visibly distinct even in a small phone mockup.

## Signature detail

Choose one intentional, product-specific detail worth capturing in a screenshot: a project cover, ledger stamp, tactile chart, progress treatment, or meaningful transition. Do not distribute decorative effects uniformly across every component.

## Color review

Check the rendered result, not only hex values:

- primary text remains readable on every surface;
- semantic positive and negative values are distinguishable without relying only on color;
- active navigation is clear but not louder than screen content;
- accent colors are repeated consistently rather than scattered;
- light and dark themes retain the same semantic mapping;
- supplied imagery does not clash with the UI palette.

## Device fidelity

Match the target platform's frame and navigation behavior. A prototype may use a desktop canvas for review, but the phone content must remain functional when the canvas disappears at a narrow viewport.
